# 优化待办与已否决方案

记录已经查证清楚、但**当前没有必要做**的优化项，以及已被实测否决的方案。
避免以后重复调研。

## 空间现状：不缺空间

```
app 分区          3.00 MB
应用实际占用      2.67 MB
剩余              421 KB (15%)
```

固件构成：

| 类别 | 字节 | 占比 |

**结论：421KB 余量够再写三倍的应用代码，空间不是瓶颈。**

## 暂缓的优化项

触发条件：**需要新增大字号中文字体时**再回来做。届时这些是唯一的空间来源。

### 1. clock_font → EN_BIG（-98,762 字节）

`clock_font` 行高 96px，**唯一使用者**是息屏时钟页的呼号标签
（`idle_clock_callsign_apply_fit_style` 与标签创建两处）。

`EN_BIG`（82px）已在固件中，且与 `clock_font` **码位范围完全相同**（0x20–0x7F，
96 个 ASCII 字符）——两者装的是同一批字符，只是字号不同。换用后
`clock_font` 失去最后一个引用，链接器 `--gc-sections` 会整个丢弃。

代价：息屏呼号矮 14px。呼号用的是动态字距（`label_apply_dynamic_letter_space`
target_width=306），横向仍会填满，只是高度变化。

**这同时是个视觉决策，应由 UI 重设计一并定夺。**

### 2. font28 → font20 / EN_BIG（-14,030 字节）

`font28`（37px）同样是 0x20–0x7F 的 ASCII 子集，仅用于主屏最近呼号标签。同上。

### 3. 字体挪到独立分区（app 减少约 1.17 MB）

已实测可行（见下方基准数据），`mmap` 后访问机制与当前 `.rodata` 完全相同，
**零延迟代价**。

收益主要是**开发时烧录时间减半**（app 2.67MB → 1.5MB）。但提高写入波特率
能以十分之一的成本获得更大提速，所以这项优先级更低。

## 已否决的方案

### ❌ 字体放 SD 卡

实测否决。SD 卡（SK32G SDHC，SPI 模式 20MHz 硬件上限）：

| 操作 | 平均 | 中位 | P95 |
|---|---|---|---|
| 偏移表项 (4B) 随机读 | 1,983 μs | 1,782 | 2,628 |
| 字形描述+位图 (175B) 随机读 | 3,653 μs | 3,494 | 4,340 |
| 整扇区 (512B) 对齐随机读 | 2,916 μs | 2,683 | 3,527 |
| 顺序 512B | 901 μs | 905 | 909 |

**一行 12 个汉字：44.3 ms**（偏移表缓存于 RAM）/ **67.9 ms**（偏移表也在 SD）。

否决理由：44ms 已是可见卡顿，而**最坏情况恰好是变化最频繁的 QTH 地名**——
每换一个说话人就是一组新地名，必然缓存未命中。字形缓存对这种场景帮助有限。

两个观察：

- **175 字节的读比 512 字节还慢**（3,653 vs 2,916 μs），因为非对齐偏移跨了两个扇区
- **瓶颈是每次操作约 2ms 的固定开销，不是带宽**。顺序读只有 547 KB/s，
  而 20MHz SPI 理论值 2.5MB/s，效率仅 22%

### ✅ 字体放内部 flash 分区（技术可行，见"暂缓项 3"）

同一测试程序的对照组，读同一块内部 flash 分区：

| 方式 | 单次 175B | 一行 12 汉字 |
|---|---|---|
| `esp_partition_read()` | 106 μs | — |
| **`mmap` + memcpy** | **15 μs** | **218 μs** |
| `mmap` + 逐字节累加 | 27 μs | — |

**比 SD 快 203 倍。** 原因：当前字体在 `.rodata` 里本来就是"内部 flash + MMU 映射"，
挪到独立分区再 `mmap` 是同一机制，所以零代价。分区被映射到 `0x3f410000`。

测试程序保留在 `firmware/sdfont-bench/`，可用
`PROJECT=firmware/sdfont-bench tools/idf.sh build flash` 重跑。

### ❌ 双 OTA 分区

4MB flash 装不下。算细账：

```
4MB 扣掉 bootloader/分区表/nvs/phy      4.13 MB
字体分区（font20 + status_font）        -1.20 MB
otadata                                 -0.01 MB
剩余给两个 OTA 槽                        2.92 MB → 每槽 1.46 MB
搬走字体后的 app                         1.50 MB   ❌ 差 40KB
```

**卡在临门一脚。** 出路只有三条，都有明确代价：

| 出路 | 代价 |
|---|---|
| 字体子集化（GB2312 一级，3,755 字） | 生僻字变豆腐块，数据驱动、测试覆盖不到 |
| 全英文 UI | **电台名全部失效**——FMO 服务器只返回中文 `name`，无英文字段 |
| 换 ESP32-WROOM-32E-N8/N16 模组 | 需热风返修拆焊模组，可能损坏板子 |

已决定**不追求 OTA**。

## 字体机制备忘

LVGL 用点阵字体，**没有缩放**——每个字号都要存一套完整字形位图。

XBF 头（`x_header_t`：`uint16 min, uint16 max, uint8 bpp`）实测：

| 字体 | 行高 | 码位范围 | bpp | 占用 |
|---|---|---|---|---|
| font28 | 37 | 0x20–0x7F | 4 | 14,030 |
| EN_BIG | 82 | 0x20–0x7F | 4 | 78,232 |
| clock_font | 96 | 0x20–0x7F | 4 | 98,762 |
| status_font | 16 | 0x0A–0x9ED1（稀疏子集） | 4 | 183,823 |
| font20 | 26 | 0x09–0xFFE5（全覆盖） | 4 | 989,009 |

要点：

- **前三个字体的码位范围完全相同**，是同样 96 个 ASCII 字符的三份副本
- **体积按面积增长**：高度翻倍，体积约翻四倍
- **`status_font` 是子集字体**，不含完整中文。显示动态地名会出豆腐块
  （实测「昆明市」渲染成 `□昆□`）。**动态中文一律用 `ui_font_cn()`（font20）**
- 全部 4bpp。降到 2bpp 可减半，代价是边缘锯齿，大字号上是否可接受未实测

字形数据可用 `objcopy` 从编译产物精确提取（不要解析 C 源码，数组里
有 69,389 行形如 `//0x9c23` 的注释会污染正则匹配）：

```bash
xtensa-esp32-elf-objcopy -O binary --only-section=.rodata.glyph_dsc_xbf \
    build/esp-idf/main/CMakeFiles/__idf_main.dir/fonts/font20.c.obj font20.xbf
```

## 省电模式实测说明

`app_power_save_enter()` 做四件事：

1. `audio_ws_stop()` —— 停止 WebSocket
2. **`wifi_manager_stop()` —— 关闭 WiFi**
3. 切到息屏时钟页
4. 背光降到 **10%**（`APP_POWER_SAVE_BACKLIGHT_PERCENT`）

估算耗电（未用电流表实测）：正常约 170mA → 省电约 60mA，**约省到三分之一**。

**没有省的两块**：

- CPU 仍满速 240MHz。`CONFIG_PM_ENABLE is not set`，代码中也无任何
  `esp_pm_configure` / `esp_light_sleep_start`，无动态调频、无轻睡眠，约剩 40mA 可挖
- 屏幕未关闭，只是调暗。ST7789 若进 sleep-in 并关背光还能再省约 15mA

**本质是"下线"而非"调暗"**：WiFi 被关闭，设备收不到任何 FMO 事件。
这解释了 `app_ui_wake_from_idle()` 里那句"省电模式下不允许业务事件唤醒"——
不是不允许，是根本没有事件可以唤醒它。

### ⚠️ 已知 bug：退出提示不可见

退出手动省电的唯一方式是**长按时钟界面**。短按会调用
`app_ui_update_status("长按退出省电")` 给出提示，但该函数写的是
`s_label_bottom_status`——**那个标签在主界面底栏上，而息屏时钟页正盖在主界面之上**。

**提示被画在了用户看不见的地方。** 实际体验是：按下节能后设备离线，
短按无反应也无提示，看起来像卡死。

修法：在息屏时钟页自身放一个提示标签。约 20 行。

**暂缓原因**：UI 重设计可能移除或改造手动节能按钮（对"插电常驻监看"定位而言，
该功能是负价值的——按下只会让设备离线），现在修可能是白干。
