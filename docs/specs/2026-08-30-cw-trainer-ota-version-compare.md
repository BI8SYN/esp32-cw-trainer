# OTA 版本比较：从「不同即有更新」改成语义比较（设计记录）

日期：2026-08-30
状态：**已实施**，随 v1.5.0 发布。
相关：`docs/release-process.md`（PROJECT_VER 是唯一权威的版本号）

## 1. 症状与真正的毛病

本机刷了 v1.5.0，而服务器清单上还挂着 v1.4.4，设备一直提示「有新版本」。

根子在 `ota.c`：

```c
/* 只比"是否不同"，不判大小：版本号是自由字符串，语义比较不可靠，而且
   服务器放旧版本时"降级"本身也是有用的操作。 */
s_chk.available = strcmp(s_chk.latest, ota_current_version()) != 0;
```

**不等即有更新。** 所以这不只是"提示烦人"——那个提示点下去会把设备**静默降级**
回 v1.4.4，而用户以为自己在升级。

### 1.1 还有一个更隐蔽的问题：strcmp 的排序本身就是错的

```
strcmp("v1.10.0", "v1.9.0") < 0        因为 '1' < '9'
```

`v1.10.0` 会被判成比 `v1.9.0` **旧**。这个工程迟早会到 v1.10，到那天所有设备都会
拒绝升级，而且不会有任何报错——比现在这个症状难查得多。也就是说，**即使不修提示，
字符串比较也必须换掉**。

### 1.2 原注释的两条理由，一条错一条对

| 原理由 | 判断 |
|---|---|
| 「版本号是自由字符串，语义比较不可靠」 | **错**。`docs/release-process.md` 把 `PROJECT_VER` 定死成 `vMAJOR.MINOR.PATCH`，它不是自由字符串，这条前提被项目自己的规则否定了 |
| 「服务器放旧版本时降级本身也是有用的操作」 | **不采纳**（见 §3.2）。救急目的成立，但手段不对——正确做法是发版本号更高的回退包 |

## 2. 为什么不加构建号

需求最初的设想是「在 json 里加一个构建号，每次构建递增，用它判断是不是最新」。
不采纳，理由三条：

**一、它解决不了这个 bug。** 毛病在**比较运算符**（`!=` 而不是 `>`），不在标识的
粒度。加了构建号仍然用 `!=`，症状一模一样；要管用还是得改成「大于才算更新」——
那既然如此，直接对版本号做大小比较就行，不必引入第二个标识。

**二、它会成为第二个权威。** `docs/release-process.md` 写得很死：`PROJECT_VER`
是**唯一权威**的版本号。两个能互相矛盾的标识是新增的故障源，而不是减少。

**三、它没有好的存放处。** 存进仓库文件 → 每次本地构建都弄脏工作区；用时间戳 →
同一个 commit 重新编出来的号不一样，失去可复现性；用 CI 计数器 → 这个项目没有 CI。

构建号唯一能补的缺口是「同一个版本号发了两个不同的包」，而 `release-process.md`
已经用 PATCH 位覆盖了这件事（「PATCH 位要真的用起来」），而且 PATCH 对用户是有
意义的，构建号不是。

## 3. 做法

### 3.1 `core/version_cmp.c`：纯函数，可测

```c
#define VERSION_CMP_BAD INT_MIN
int version_cmp(const char *a, const char *b);   /* 语义同 strcmp */
```

接受 `v1.5.0` / `1.5.0`（v 可选）/ `v1.5`（缺位补 0）/ `v1.5.0-keytest`（后缀忽略，
只比三段数字）。冒烟测试用过 `v1.5.0-keytest` 这种版本号，它和已发布的 `v1.5.0`
应该算同一版，不该互相提示升级。

解析失败返回 `VERSION_CMP_BAD` 这个哨兵，**不是 0**：0 的意思是「两边一样新」，
把「看不懂」和「一样新」混为一谈会让调用方无法区分该不该提示。

放进 `core/` 是因为它是纯逻辑，主机侧单测能直接跑——`test_version_cmp.c` 8 条，
其中 `two_digit_parts_are_not_compared_as_text` 专门钉住 §1.1 那个坑。

### 3.2 只往前走，不给降级入口

`available`（服务器版本严格更新）是「能不能升级」的**唯一**判据。清单上挂着更旧的
版本时，设备就当自己已经是最新的，界面上不出现任何往回装的入口。

> **这一条推翻了本文档初稿。** 初稿里保留了降级通道，升级页在服务器版本更旧时把
> 按钮改成「装旧版」。真机上看到那个按钮之后决定去掉——**不想让用户 OTA 降级**。
> 理由是那个按钮出现在普通用户面前，而按下去的后果他不理解；而这也是主流 OTA
> 系统的常规做法：版本号只往前走。

救急目的并没有丢，只是换成正着走：要把设备拉回旧代码，**发一个版本号更高的回退包**
（例如 v1.5.1 的内容是 v1.5.0 的回滚）。这比开放降级更好——版本号只往前走，设备上
装了什么永远能由版本号唯一确定，不会出现「两台都显示 v1.4.4，一台是升上来的、
一台是降下来的」这种分不清的状态。

另有一层与此无关的兜底：新固件启动后没调 `ota_mark_valid()` 就崩了或断电，
bootloader 会自动回滚到旧槽（`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`）。

解析不了时 `available` 保持 false，**不猜**。把一个看不懂的版本号猜成「更新」，
代价是把用户装上一个不知道是什么的固件。同时打一条 `ESP_LOGW`，让这件事可观察。

服务器版本更旧时设置页显示「已最新」——这不是谎话，用户确实在跑最新的那一版。
服务器上挂着哪一版仍然能在升级页看到（「最新版本 v1.4.4」），诊断信息没丢。

## 4. 顺带修了 check_charset.py 的一个假阳性

新加的 `ESP_LOGW` 让 `tools/check_charset.py` 报出 `析` 和破折号缺字。追进去发现：
**诊断字符串（`ESP_LOG*`、`_Static_assert` 的消息）是字符串字面量，会被算进「界面
用到的字」**，而它们永远不会出现在屏幕上。

这不是小事。字库大小直接决定 OTA 能不能用——`main/ota.h` 写着「裁剪字库前固件
2.2MB，双槽根本放不下，所以字库裁剪是这个功能的前提」。

`used_chars()` 里加一步 `strip_diagnostics()`：手写扫描找到 `ESP_LOG[EWIDV]` /
`ESP_EARLY_LOG*` / `_Static_assert` 的调用，跟踪字符串与转义数到配对的右括号，
整段删掉。不能用正则一把梭——参数里就有括号和引号（`"服务器返回 %d (%s)"`）。

效果：界面字符数 389 → 370，裁剪字库 60.6KB → 55.5KB。被排除的 19 个字
（`—义事历史备实尚必条析每注真证释项须首`）逐个回查过，确认没有一个出现在非诊断的
字面量里——**假阴性会让屏幕上出现空白，比多几个字形严重得多，这一步不能省。**

同期还改了一处：`cw_settings.c` 里两条 `_Static_assert` 的消息本来是中文，白白带进
`冻布局改` 四个字。已改成 ASCII——编译器诊断本来也该是 ASCII。

## 5. 不做的事

- **不加构建号**，理由见 §2。
- **不提供降级入口**，见 §3.2。要回退就发版本号更高的回退包。
- **不改 `publish_ota.sh` 的清单格式**。`{"version":..., "url":...}` 两个字段够用，
  加字段就要考虑老固件读新清单的兼容性，收益为零。
