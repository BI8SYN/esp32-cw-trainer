# CW Trainer 交互音效设计

日期：2026-09-01
状态：设计定稿

## 1. 出发点与硬约束

给判断结果、导航操作、异常状态加声音反馈。

**这台机器只有一个振荡器。** `tone_gen_set(bool)` 是单一频率的开关，四个生产者
共用它：电键侧音（`key_input.c` 的 5ms 任务）、收报回放（`kob_net.c`）、文本发报
（`cw_player.c`），现在再加上提示音。没有第二音色、没有和弦，能变的只有**频率、
时长、节奏**。

于是有一条别的产品不会遇到的约束：

> **任何提示音，在一只受过训练的耳朵里都会被听成莫尔斯。**

这个项目已经就此表过态。`main.c` 里开机音选 `V`（历史上的试机信号 VVV）的理由是
「这台机器是训练器，**它发出的每个声音都是教材**，不能拿一个语义不对的信号天天
教人」。

## 2. 三个已确认的决定

1. **提示音刻意做成「不是莫尔斯」**，而不是用 CW 缩略语。
   （否决的另一条路：判对 = `R`(Roger)、判错 = 八个点(HH，电报里真正的「我发错了」)。
   很贴产品，但声音长——20 WPM 下八个点约 0.5 秒——按钮点击这种高频事件用不了。）
2. **点击音只给「焦点之外」的操作**：导航类按钮响；听写键盘、选项卡、重播这些
   「正在做题」的控件不响——那些时刻耳朵在干正事，多一个声音就是干扰。
3. **跟随现有音量，不加新设置。** 音量调到 0 就全静音。

## 3. 为什么「静音多久」不足以判忙闲

最容易想到的仲裁是「安静满 N 毫秒就算空闲」。**它在这台机器上是错的**：听写播放
在字符之间本来就有长静音，Farnsworth 间距下更长。纯靠静音时长，提示音会正好落进
听写的字间隔里——恰恰是最糟的位置。

所以分两层：

- **会话占用** `tone_gen_hold(bool)`：仿照已有的 `tone_gen_amp_hold()`。
  `cw_player_play()` 开始时置上、DONE/STOPPED 时放开。整个听写/预告/试听会话期间
  提示音一律丢弃。
- **静音门闩** 150ms：管电键侧音和收报回放这类没有结构化长间隔的路径。

两条覆盖之后，剩下的抢占（提示音播到一半用户按了电键）由 `tone_task` 里 `s_on`
转真时**立即中止 blip 并交还**兜底。

## 4. 为什么仲裁放在 tone_gen 里

被否决的方案 B 是新建 `ui_sound.c` 向 `cw_player`/`key_input`/`kob_net` 各查一个
`is_busy()`。那需要三个新的公开查询接口，而且让 UI 层认识所有音频模块——耦合方向
反了。

方案 A 把仲裁放在**被抢的那个资源**上：`tone_gen` 是四个生产者唯一的交汇点，它
观察的是资源的真实状态，而不是各家的意图。四个生产者继续互不认识。

这和 `kob_net` 已有的做法同源：那里用「本机最后一个边沿之后静默满 `TX_BUSY_MS`
才算发完」判忙闲，而不是去问 `key_input`。

实现落在 `tone_task` 里是自然的——那个任务本来就每 2ms（`BLOCK_SAMPLES 64`
@ 32kHz）读一次 `s_on`，序列播放采样级精确、不用额外定时器，**抢占检查是免费的**。

## 5. 接口

```c
/* tone_gen.h */
typedef struct { uint16_t hz; uint16_t ms; } tone_step_t;  /* hz=0 表示静音间隔 */
void tone_gen_seq(const tone_step_t *steps, uint8_t n);    /* 被占用就整段丢弃 */
void tone_gen_hold(bool hold);                             /* CW 会话期间占住 */
```

**整段丢弃而不是逐个 blip 判断**——半截的提示音比没有提示音更糟。

```c
/* ui_sound.h */
typedef enum { UI_SND_TAP, UI_SND_OK, UI_SND_MISS, UI_SND_UNLOCK, UI_SND_FAULT } ui_sound_t;
void ui_sound(ui_sound_t s);
```

UI 侧只见语义，不碰频率时长。

## 6. 声音表

blip 频率按**当前侧音的倍数**取（`cw_settings_get()->tone_hz`），用户改音调时相对
关系不变。

| 事件 | 序列 | 总时长 |
|---|---|---|
| `TAP` 导航点击 | ×2 | 20ms |
| `OK` 判对 | ×2 → 静 → ×3 | 20+40+20 |
| `MISS` 判错 | ×3 → 静 → ×2 | 20+40+20 |
| `UNLOCK` 课次解锁 | ×2 → 静 → ×3 → 静 → ×4 | 20+40+20+40+20 |
| `FAULT` 异常 | ×0.5 | 120ms |

两条让它不像莫尔斯：**20ms 短于 40 WPM 的点（30ms）**；**序列内频率在变，而莫尔斯
从不变频**。

`tone_gen` 的 5ms 淡入淡出包络照常起作用，20ms 的 blip 是「5 升 + 10 平 + 5 降」，
不会爆音。

## 7. 接入点

| 位置 | 事件 |
|---|---|
| `ui_common.c` 的 `make_btn` / `ui_chip` | `TAP` |
| `ui_practice.c` 判分 | `OK` / `MISS` |
| `ui_result.c` 达标 | `UNLOCK` |
| 音频初始化失败的提示条 | `FAULT` |
| `ui_net.c` 进入 `ERR_WIFI` / `ERR_SERVER` | `FAULT` |

`make_btn` 统一加 `TAP` 之后，用 `ui_no_tap(obj)` 给「焦点之内」的控件退订：
听写键盘、四选一选项卡、电键桨。退订而不是逐个订阅，是因为**默认响、少数例外**
比反过来更不容易漏。

## 8. 明确不做

- **「未达标」不出声。** Koch 方法的前提就是错着学，一课十组错几组是常态；给常态
  配失败音，练一小时就是几十次惩罚。没有达标音本身已经是反馈。
- **不加设置开关。** 见决定 3。
- **不做音量独立控制。** 提示音走 `s_amp`，和侧音同一个音量。

## 9. 验证

- `tone_step_t` 序列的构造是纯函数，进 `test/` 做主机测试（给定事件与侧音频率，
  断言产出的频率与时长）。
- **仲裁行为只能靠耳朵。** 画面指纹巡检对声音一无所知，导图也一样。所以
  「提示音会不会落进听写的字间隔」这条要如实记进 README 的「尚未在真实设备上
  验证的事项」，不要假设它已经没问题。
